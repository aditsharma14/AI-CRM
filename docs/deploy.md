# Deploying Nimbus CRM

Production is three free-tier services. The browser only ever talks to Vercel; Vercel proxies `/api/*` to the API.

```
 browser ── https://nimbus-crm.vercel.app ──▶ Vercel (static frontend/dist)
                 │  /api/*  (frontend/vercel.json rewrite, same origin, never cached)
                 ▼
        https://nimbus-crm-api.onrender.com  ──▶ Render web service (backend/Dockerfile, Singapore)
                                                        │ MONGO_URI (TLS)
                                                        ▼
                                              MongoDB Atlas M0 (AWS Mumbai, 3-node replica set)
```

The AI service is not deployed yet (S2.1).

| Service | Host, plan, region | Limits that matter |
|---|---|---|
| Frontend | Vercel Hobby | rewrites to an external origin time out at **120 s** (502 `ROUTER_EXTERNAL_TARGET_ERROR`) |
| API | Render Free web service, Singapore | sleeps after **15 min** idle, about **1 min** to wake; **750 instance-hours / month** per workspace; no static outbound IP |
| Database | Atlas M0, AWS ap-south-1 (Mumbai) | 0.5 GB, 500 connections, 100 ops/s; paused after 30 days with no connections; **no backups** on M0 |

## 1. Before you start: generate the JWT secret

Run this locally and keep the output for step 3. Never commit it or paste it anywhere but Render.

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

That's 96 hex characters; production refuses anything shorter than 32 or equal to a placeholder.

## 2. MongoDB Atlas

1. Sign in at <https://cloud.mongodb.com> (Google or GitHub is fine).
2. **Create a project:** top-left project menu → **New Project** → name `Nimbus CRM` → **Next** → **Create Project**.
3. **Create the cluster:** **+ Create** (or **Build a Database**) → **M0** (Free) → Provider **AWS** → Region
   **Mumbai (ap-south-1)**. If Mumbai isn't offered for M0, choose **Singapore (ap-southeast-1)**, the same region as
   the API. Name it `nimbus-crm` → untick "Preload sample dataset" → **Create Deployment**.
4. The "Connect to nimbus-crm" dialog asks you to create a user. Close it (or skip that step); the user is made next
   with narrower rights than the dialog would give.
5. **Database user with access to `nimbus-crm` only:** left menu **Security → Database Access** → **+ Add New Database
   User**:
   - Authentication Method: **Password**. Username: `nimbus-api`.
   - Password: **Autogenerate Secure Password** → **Copy**. Keep it for step 7.
   - Database User Privileges: **Add Specific Privilege** (not "Built-in Role", and never `atlasAdmin`) → Role
     **readWrite**, Database **nimbus-crm**, Collection left empty.
   - **Add User**.

   `readWrite` on one database is enough: it covers the transactions lead conversion uses and the index builds Mongoose
   does at startup.
6. **Network access:** **Security → Network Access** → **+ Add IP Address** → **Allow Access from Anywhere**
   (`0.0.0.0/0`) → **Confirm**. Render's free tier has no static outbound IP, so there is nothing narrower to allow;
   the generated password is what protects the database (see Known limitations).
7. **Connection string:** **Database → Clusters** → **Connect** on `nimbus-crm` → **Drivers** → copy the
   `mongodb+srv://…` string. Put the password in and add the database name before the `?`:

   ```
   mongodb+srv://nimbus-api:<password>@nimbus-crm.<id>.mongodb.net/nimbus-crm?retryWrites=true&w=majority&appName=nimbus-crm
   ```

   If the generated password has characters like `@ : / ? #`, percent-encode them (Atlas's autogenerated ones are
   alphanumeric). This is `MONGO_URI`.

## 3. Render (the API)

1. Sign up at <https://dashboard.render.com> **with GitHub**, and give Render access to `aditsharma14/AI-CRM`.
2. **+ New → Web Service** → pick the `AI-CRM` repository → **Connect**.
3. Settings on the create page:
   - **Name:** `nimbus-crm-api` (gives `https://nimbus-crm-api.onrender.com`; if Render adds a suffix, tell me the URL,
     because `frontend/vercel.json` names it).
   - **Language / Runtime:** **Docker**. **Branch:** `main`. **Region:** **Singapore**.
   - **Root Directory:** `backend` (Dockerfile path stays `./Dockerfile`).
   - **Instance Type:** **Free**.
   - **Environment Variables:** add each row of the "Render" part of the table in section 6. Paste `MONGO_URI` and
     `JWT_ACCESS_SECRET` here and nowhere else. For `CLIENT_ORIGIN`, use `https://nimbus-crm.vercel.app` for now; step
     4.5 corrects it if Vercel gives a different domain.
   - **Advanced → Health Check Path:** `/api/v1/health`.
   - **Advanced → Auto-Deploy:** **After CI Checks Pass** (see "Deploys wait for CI" below). If the create page doesn't
     offer it, set it afterwards: service → **Settings → Build & Deploy → Auto-Deploy**.
   - Leave **Build Filters** empty: every commit must deploy, so `/api/v1/health` reports the commit `main` is at.
4. **Deploy Web Service.** The first build takes a few minutes. When the status is **Live**, check it:

   ```bash
   curl https://nimbus-crm-api.onrender.com/api/v1/health
   # {"success":true,"data":{"status":"ok","commit":"<full sha>"},"error":null,"meta":null}
   ```

   The logs' `listening` line shows `"nodeEnv":"production"` and `"trustProxy":2`.

## 4. Vercel (the frontend)

1. Sign up at <https://vercel.com/signup> **with GitHub** (Hobby plan).
2. **Add New… → Project** → **Import** `aditsharma14/AI-CRM`.
3. **Project Name:** `nimbus-crm`. **Framework Preset:** Vite. **Root Directory:** **Edit → `frontend`**. Build command
   `npm run build` and output `dist` are the Vite defaults. **Environment Variables:** none.
4. **Deploy.** Vercel builds from `frontend/`, where `vercel.json` holds the `/api/*` rewrite and the SPA fallback.
5. Note the production domain (**Project → Settings → Domains**, normally `nimbus-crm.vercel.app`). If it differs from
   `https://nimbus-crm.vercel.app`, set Render's `CLIENT_ORIGIN` to it (Render → service → **Environment** → edit →
   **Save, rebuild, and deploy**).

## 5. GitHub

1. Repo → **Settings → Secrets and variables → Actions → Variables** tab → **New repository variable**:
   `PROD_URL` = `https://nimbus-crm.vercel.app` (no trailing slash). It's not a secret.
2. That turns on the two scheduled workflows below; until it exists they skip.

Then send me the Vercel URL, the Render URL and the Atlas region you got. I run the smoke test and the checklist in
section 7.

## 6. Environment variables

| Name | Service | Example | Secret? |
|---|---|---|---|
| `NODE_ENV` | Render | `production` (the Dockerfile's default; no need to set it) | no |
| `MONGO_URI` | Render | `mongodb+srv://nimbus-api:<password>@nimbus-crm.<id>.mongodb.net/nimbus-crm?retryWrites=true&w=majority` | **yes** |
| `JWT_ACCESS_SECRET` | Render | 96 hex characters from section 1 | **yes** |
| `CLIENT_ORIGIN` | Render | `https://nimbus-crm.vercel.app` | no |
| `TRUST_PROXY` | Render | `2` (Vercel's rewrite, then Render's ingress) | no |
| `EMAIL_ENABLED` | Render | `false` (no email provider until S2.6) | no |
| `ACCESS_TOKEN_TTL` | Render | `15m` (default) | no |
| `REFRESH_TOKEN_TTL` | Render | `7d` (default) | no |
| `RATE_LIMIT_WINDOW_MS` | Render | `60000` (default) | no |
| `RATE_LIMIT_MAX` | Render | `100` (default) | no |
| `LOG_LEVEL` | Render | `info` (default) | no |
| `PORT` | Render | set by Render; don't add it | no |
| (none) | Vercel | the API's URL is in `frontend/vercel.json`, which is public anyway | — |

## 7. Checking a deploy

- **Smoke test** (also what CI runs): `node scripts/smoke.mjs https://nimbus-crm.vercel.app`. It waits out a cold start,
  registers an org named `smoke-<timestamp>` whose owner is `smoke+…@smoke.nimbus.invalid`, creates and converts a lead,
  refreshes, deletes its lead and deal, and logs out. Smoke orgs are marked `isSmoke` by the API;
  `node backend/scripts/count-smoke-orgs.js` (with `MONGO_URI` set) counts them, read-only.
- **By hand:** register; log in; reload the page and stay signed in (the refresh cookie works through the proxy); log
  out; create and convert a lead; move a deal's stage; invite a member and **Copy invite link**; hit the API more than
  100 times in a minute and get the JSON `RATE_LIMITED` 429.

## 8. Rolling back

- **API:** Render → `nimbus-crm-api` → **Events** (or **Deploys**) → the last good deploy → **Rollback**. Render then
  pauses auto-deploy; turn it back on after the fix lands.
- **Frontend:** Vercel → project → **Deployments** → the last good one → **⋯ → Instant Rollback**.
- **Code:** `git revert <sha>` and push to `main`; CI passes, then Render and Vercel deploy the revert.
- **Data:** there are no migrations to undo (Mongoose schemas only). M0 has **no backups**: before anything risky, take
  one with `mongodump --uri "$MONGO_URI" --out backup-$(date +%F)`.

## 9. Rotating secrets

- **JWT secret:** generate a new one (section 1), paste it into Render's `JWT_ACCESS_SECRET`, **Save, rebuild, and
  deploy**. Access tokens signed with the old secret stop working at once, but sessions survive: refresh tokens are
  random values stored hashed, not JWTs, so the next API call gets a 401, the client refreshes, gets a token signed with
  the new secret and retries. Nobody is signed out. The old secret is useless from then on.
- **Database password:** Atlas → **Database Access** → `nimbus-api` → **Edit → Edit Password → Autogenerate** → **Update
  User**, then put it into Render's `MONGO_URI` and redeploy. The API can't reach the database between those two
  steps, so do them back to back.

## 10. Deploys wait for CI

`main` takes direct pushes, so Render deploys only **After CI Checks Pass**: it waits for every check GitHub reports on
the commit and skips the deploy if any fails, or if there are none. Render counts `success`, `neutral` and `skipped` as
passing. The production workflows are built so they can never block or deadlock a deploy:

- **[keep-warm.yml](../.github/workflows/keep-warm.yml)** pings `/api/v1/health` every 10 minutes from **08:00 to 23:00
  IST** (02:30–17:30 UTC) and always ends green. When the API reports `main`'s head as deployed and no smoke run exists
  for that commit yet, it dispatches deploy-smoke. That's the "after each push, once the deploy finishes" smoke.
- **[deploy-smoke.yml](../.github/workflows/deploy-smoke.yml)** (every 6 hours, on dispatch) runs the smoke test only if
  the API reports the commit it runs for. Otherwise it ends green with a notice, and fails only if `main`'s head is more
  than 20 minutes old and still not deployed (a deploy that never happened). A smoke run therefore never sits pending on
  a commit Render is still waiting to deploy.
- Without the `PROD_URL` variable both jobs are skipped, which also passes.

**Hour budget:** keep-warm holds the API up about 15 hours a day (02:30–17:30 UTC, plus up to 15 idle minutes before it
sleeps): **≈ 465 of the 750** monthly free hours in a 31-day month (at most about 473). The rest, **≈ 277 hours**, is
room for the S2.1 AI service on the same workspace. Outside those hours the API sleeps, and the first request pays the
cold start, which the frontend rides out ("Waking up the server…", retries for about 90 s).

## Known limitations

- **Direct requests to the Render origin bypass Vercel** ([#26](https://github.com/aditsharma14/AI-CRM/issues/26)).
  `TRUST_PROXY=2` believes the last two `X-Forwarded-For` hops. A client calling `nimbus-crm-api.onrender.com` directly
  can put any address there and get a fresh rate-limit bucket per request. The fix is Vercel's documented one: a secret
  header set on every rewrite and checked by the API. Not built yet.
- **Atlas allows `0.0.0.0/0`.** There's no static IP to allow on Render's free tier; the database relies on its
  generated password and a user limited to `readWrite` on `nimbus-crm`.
- **No database backups on M0.** Take a `mongodump` before risky changes (section 8).
- **Cold starts** from 23:00 to 08:00 IST, and whenever a scheduled ping is late (GitHub delays scheduled runs under load,
  and disables them in a repo with no activity for 60 days).
- **Smoke orgs accumulate**, a few KB per run against the 0.5 GB limit. They are marked `isSmoke` and counted by
  `count-smoke-orgs.js`. Nothing cross-org shows them today (every read is org-scoped), and any future cross-org view
  should filter on `isSmoke`.
- **No email.** `EMAIL_ENABLED=false`: no password reset, and invite links are copied by the inviting admin (S2.6).
